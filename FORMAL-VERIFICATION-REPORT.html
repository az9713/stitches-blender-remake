1. Bottom line

9rules checked
5rules break: 5 bugs
4rules hold
930existing frames clean

This project renders a film in two steps: tools/render_frames.py makes one PNG per frame, and tools/post.py joins the PNGs into an MP4. The check tested one promise of these two scripts: a stopped run can resume safely, and "OK" means the whole film.

The promise is not fully true. 5 of 9 rules break. For example, a resumed render can keep a 0-byte frame, and post.py can print "OK" for a film with 1 frame or 0 frames. Bugs 1 to 4 reproduced with real Blender, cv2, and ffmpeg. Bug 5 reproduced with a stand-in for ffmpeg.

The existing film is not damaged by these bugs. All 930 frames in build/frames have a PNG end chunk, and none is older than build/scene.blend. stitches_final_v2.mp4 has 930 video packets and a duration of 31.031 s. These checks do not judge pixel content.

Workaround: use a new frame folder after each scene rebuild. This prevents bug 4. Until the bugs are repaired, also look for a 0-byte f*.png after a stopped render, and count the film's frames after post.py. No product code was changed.

2. The method

pstack and create-formal-verification-skill

pstack is a plugin of agent workflows for Cursor and Claude Code, by Lauren Tan. This work used version 0.15.36. A skill in pstack is a folder with a SKILL.md file. A coding agent reads that file and follows its instructions.

create-formal-verification-skill tells the agent to do these things:

  1. Find the code where a bug costs the most and tests reach the least.
  2. Select the verification tool that fits the question.
  3. Verify the promise, and show each property failing on a broken variant.
  4. Report any break as a finding. Do not weaken the property, and do not change product code.
  5. Generate a project-local skill that a later agent can run. Here that skill is .claude/skills/verify-frame-pipeline/.
  6. Test the generated skill once on a scratch break in the real code, then drop the break.

The agent followed these instructions by reading the file. It ran the tools in WSL Ubuntu, because a pstack helper for TLC output, /statechart, fails on native Windows with spawn /bin/sh ENOENT.

TLA+ and TLC

TLA+ is a language for describing a system as states and the steps between states. The model here has 15 steps, such as "Blender opens the PNG", "the render is stopped", and "post.py finishes". A rule (TLA+ calls it an invariant) is a statement that must be true in each state.

TLC is the model checker for TLA+. It starts from the initial state, applies every possible step, and continues until it finds no new state. If a rule is false in a state, TLC gives the sequence of steps that reaches that state. This sequence is a counterexample. TLC searches breadth-first by default, so the first counterexample it finds is a shortest one.

This is one model step and one rule, from FramePipeline.tla:

SkipFrame ==
    /\ rp = "checking" /\ ri <= N
    /\ (ri \notin Listed \/ Skips(ri))
    /\ ri' = ri + 1
    /\ UNCHANGED <<png, scene, rp, redid, stops, rebuilds>> /\ UNCHANGED postVars

OKMeansEveryFrame == pp = "ok" => {encoded[i].f : i \in DOMAIN encoded} = Frames

In words: the render job can skip the current frame and move to the next. The rule says that when post.py has printed OK, the set of encoded frames equals the set of all frames.

Why exhaustive checking finds what tests miss

A test checks one sequence that someone thought to write. Bug 1 needs a specific order of events: a stop in the 0.3 s when a PNG is open, then a restart, then an encode. A normal render followed by a normal encode passes, and the real film did pass.

TLC does not need anyone to imagine the order. At the bounds in section 4, it searches every order of stops, restarts, rebuilds, overlaps, and encodes: 20,819 distinct states.

The limit: this search covers the model, not the code. A model can describe code that does not exist. The next two parts of the method reduce that risk.

How check.py measures 11 facts from the real code

A TLA+ model does not read Python, so it cannot see a code change by itself. check.py connects the two. It runs the real scripts against scripted cases, records what they do, and sets the model's constants from the results. Then it runs TLC once per rule.

It fakes only the edges that are slow or absent in WSL:

  • bpy (Blender's Python API): a mock. Its render call writes a small valid PNG at the path that the script selected, or a 0-byte file and then a simulated stop.
  • cv2 and numpy: mocks, so the check needs no packages.
  • ffmpeg: a small shell script on PATH. It records its arguments and its input, then exits with a selected code.

Two further controls apply in the video() cases. finish(), the image-processing function, is replaced by a stub, because its image work needs the real cv2 and numpy. glob.glob returns files in reverse order, so that a missing sort shows. A separate case runs the real finish() with cv2.imread returning None.

Replays with real tools

A counterexample is a claim about the model. It becomes a bug only when the real code reproduces it. The agent replayed each one on Windows 11 with Blender 5.2.1, cv2 4.13.0, and ffmpeg 7.1.1, in a scratch folder. The test scene was a small noisy plane at 1080x1920, rendered at 1 sample on the CPU. Each test PNG was 4,610,528 bytes. build/frames and the real scene were not used.

Two of those measurements also set the model:

  • The PNG write is not one indivisible step. The final name appeared at 0 bytes, then showed the full size 0.29 s to 0.41 s later (3 frames). A kill of the Blender process on first sight of f0002.png left a 0-byte file.
  • cv2 rejects a PNG cut short. cv2.imread gave None at all 9 cut positions: 0, 40, 46,105, 1,152,632, 2,305,264, 3,457,896, 4,564,422, 4,610,066, and 4,610,516 bytes. The last position keeps all the data and removes only the end chunk.

3. The code under test

The project is a 31-second vertical video of a stitched leg wound healing, built as real 3D in Blender. No AI video generator makes any picture. It has 930 frames at 30000/1001 frames per second. Blender renders each frame with Cycles at 1080x1920, and post.py grades it and upscales it to 1296x2304.

4. The promise, the rules, and the bounds

The promise. After any order of stops, restarts, and scene rebuilds, a finished render leaves a complete frame for each listed number, and "OK" from post.py means the film holds each frame once, in order, complete, and from the current scene.

The promise is written as 9 rules, one for each way it can break. "Shortest path" is the number of steps in TLC's shortest counterexample.

RulePlain sentenceResultShortest path
ResumeNeverKeepsDamagedFrameA finished render run leaves no frame file cut short.BREAKS10 steps
ResumeRedoesNoFinishedWorkA restart does not render a finished frame of the current scene again.HOLDSNone
RunCoversEveryFrameA finished render run leaves a file for each listed frame.HOLDSNone
FramesStayInOrderThe film takes frames in frame-number order.HOLDSNone
OKMeansEveryFrameWhen post.py prints OK, the film has every frame.BREAKS3 steps
OKMeansNoDamagedFrameWhen post.py prints OK, the film has no frame cut short.HOLDSNone
OKMeansOneSceneWhen post.py prints OK, every frame comes from the current scene.BREAKS9 steps
OKMeansFfmpegSucceededWhen post.py prints OK, ffmpeg succeeded.BREAKS4 steps
FilmNameAlwaysWholeThe film's final name never holds an unfinished film.BREAKS1 step

Bounds

BoundValue
Frames3

The model has one render job and one post.py job, and these two jobs can overlap. Two further rules, called witnesses, must break on each run. They prove that the model reaches "render finished" and "post.py printed OK", so the rules that start from those states are not empty.

Why 930 frames is reasoned, not proven

TLC searched 3 frames, not 930. The extension rests on this argument:

  • Both loops treat each frame in the same way. No branch that affects the output files depends on the frame number, other than sorting.
  • 3 frames provide a first, a middle, and a last frame, so a gap and an order error can both occur.
  • More frames therefore add longer paths, and the argument finds no new kind of step.
  • The 5 breaks use steps that exist at any frame count. The replays reproduced them on folders of 0 to 3 frames, not on 930 frames.

This is an argument, not a proof. No one ran TLC at 930 frames, and no symmetry proof was written. For a rule that holds, the pass is a result for these bounds only. The fact cases for post.py did use the frame numbers 1 to 930. The fact cases for render_frames.py used frames 1 to 3.

5. The 5 bugs

The bug numbers match the findings in SKILL.md. The evidence level says what reproduced each bug.

Bug 1: a resume keeps a damaged frame

Rule broken
ResumeNeverKeepsDamagedFrame
Cause
render_frames.py:23, if os.path.exists(path):, treats "the file exists" as "the frame is complete". render_frames.py:25-26 writes directly to the final name, so an incomplete file can exist.
Steps
  1. Blender opens f0002.png, and the file exists at 0 bytes.
  2. The Blender process stops. f0002.png stays at 0 bytes.
  3. The same render command runs. It skips frames 1 and 2, renders only frame 3, and ends normally with exit 0.
  4. post.py reaches frame 2 and crashes at post.py:47: AttributeError: 'NoneType' object has no attribute 'astype'.
  5. Each restart repeats steps 3 and 4 until someone finds the file.
Harm
The render reports success with a damaged frame, and the failure appears only in the later encode. The crash occurs when post.py reaches that frame, so a late frame costs up to the full encode time, about 35 minutes.
How likely
Estimate, not a measurement: about 0.3 s of a 22.7 s mean frame is 1.3%, so about 1 stop in 75 lands in the write. The test scene's file was larger than the real frames (1.8 MB to 3.3 MB), and the real render used the GPU.
Evidence level
Reproduced with real tools. Real Blender was killed in the write, then real render_frames.py, cv2, and ffmpeg ran.
Fix direction
Render to a temporary name, then rename with os.replace after Blender returns. Also make the skip test confirm the PNG end chunk, so that older damaged files are rendered again. Test the temporary name with real Blender, because Blender's handling of output names was not tested.

Bug 2: a crash or stop replaces the good film

Rule broken
FilmNameAlwaysWhole
Cause
post.py:79-81 starts ffmpeg -y on the final name, [out_path], before it processes a frame.
Steps
  1. A 3-frame film has the final name.
  2. post.py starts on a frame folder with a damaged frame 2. ffmpeg overwrites the film's name.
  3. post.py sends frame 1, then crashes on frame 2.
  4. The final name now holds a 1-frame film. The 3-frame film is gone.
Harm
A previous good film is lost, and the file under its name looks finished. The real stitches_final_v2.mp4 took about 35 minutes to encode.
Evidence level
Reproduced with real tools: the frame count measured with ffprobe went from 3 to 1. A user stop in this project also left a 2,359,344-byte file under the final name.
Fix direction
Encode to a temporary name such as out.partial.mp4, and rename it only after ffmpeg exits 0.

Bug 3: OK with frames missing

Rule broken
OKMeansEveryFrame
Cause
post.py:78 takes whichever files exist, and post.py:89 prints OK with no comparison against the expected list.
Steps
  1. A render is stopped after frame 1, so only f0001.png exists.
  2. post.py runs on the folder.
  3. It prints OK and exits 0. The film has 1 frame.
  4. On an empty folder, it prints OK film.mp4 0 frames and exits 0. The file is 261 bytes and has no frames.
Harm
A short or empty film looks finished. The printed count is the only sign, and nothing compares it with 930.
Evidence level
Reproduced with real tools.
Fix direction
Before encoding, compare the files with the expected frame numbers, and stop with a non-zero exit if any is missing.

Bug 4: OK with frames from an old scene

Rule broken
OKMeansOneScene
Cause
render_frames.py:23 does not compare a frame with the scene, and post.py:78 and post.py:89 do not either. Nothing removes old frames after a rebuild.
Steps
  1. All frames exist from an earlier scene.
  2. The scene file is rebuilt.
  3. The same render command runs and renders 0 frames, because all files exist. The frame files stay unchanged.
  4. post.py prints OK. The film shows the old scene.
  5. If a stop came before the rebuild, the folder can hold frames from two scenes: old frames that stay, and new frames for those that were missing.
Harm
A scene fix does not reach the film, or reaches only part of it, and every message reports success. The project's own notes say that a geometry change needs a rebuild and a new render.
Evidence level
Reproduced with real tools for steps 1 to 4. The "rebuilt" scene was a copy with a newer time and the same content. That is sufficient here, because the skip test does not read the scene. Step 5 follows from the same lines and was not replayed.
Workaround
Use a new frame folder after each scene rebuild.
Fix direction
Key the frame folder to the scene, or skip a frame only if it is newer than the scene file. Make post.py apply the same test.

Bug 5: OK when ffmpeg failed

Rule broken
OKMeansFfmpegSucceeded
Cause
post.py:88-89: p.wait() returns ffmpeg's exit code, nothing reads it, and the next line prints OK.
Steps
  1. The stand-in for ffmpeg reads all its input, then exits 1.
  2. post.py prints OK and exits 0.
  3. No film file exists.
Harm
A failed film looks finished, and a script that runs after post.py sees exit 0.
Evidence level
Stand-in only. The real post.py, cv2, and frames ran, but a small program took the place of ffmpeg. No real ffmpeg failure at the end of a file, such as a full disk, was produced. By reasoning only, and not tested: an ffmpeg failure at the start would probably raise a broken-pipe error at the frame write, and so would not print OK.
Fix direction
Read the code from p.wait(). If it is not 0, exit non-zero and do not print OK.

How the bugs combine

Bugs 1 and 2 form a chain

  1. A stop leaves a 0-byte frame (bug 1).
  2. The resume skips it and reports success (bug 1).
  3. post.py starts, and ffmpeg -y overwrites the good film's name (bug 2).
  4. post.py crashes at the damaged frame (bug 1).
  5. The good film is gone, and a short film has its name (bug 2).

So one stop in the 0.3 s write can cost one frame and the previous film. The crash gives exit 1, so this chain is visible. Bug 2 does not need bug 1: any crash or stop of post.py has the same effect on the film's name.

Bugs 3, 4, and 5 share a root cause

post.py:89 prints OK whenever the loop ends. It does not test the three things that "OK" should mean: all frames present (bug 3), all frames from the current scene (bug 4), and ffmpeg successful (bug 5). In all three cases, post.py prints OK and exits 0.

One further link: bugs 1 and 4 both come from render_frames.py:23, where "the file exists" stands for both "complete" and "current".

Suggested repair order

This is a suggestion. Nothing has been repaired.

  1. Bugs 5 and 3: small tests in video(), with no change to the output file.
  2. Bug 2: a temporary film name. It protects the existing film from every later failure.
  3. Bug 1: a completeness test and a temporary PNG name, tested with real Blender.
  4. Bug 4: a scene test, after a decision on how to key frames to a scene.

6. What holds, what is not covered, and the assumptions

The 4 rules that hold

RuleThe code that guards itWhat it means in practice
ResumeRedoesNoFinishedWorkrender_frames.py:23-24A restart keeps finished frames. A 5.85-hour render is not lost. The same line causes bugs 1 and 4, so a repair must keep this behavior for a complete, current frame.
RunCoversEveryFramerender_frames.py:21-26A run that reaches the end of its list leaves a file for each listed number. The file can still be damaged (bug 1).
FramesStayInOrderpost.py:78Frames reach ffmpeg in number order, whatever order the file system gives.
OKMeansNoDamagedFramepost.py:47A frame cut short stops the run, so it cannot enter a film that gets "OK". This is a side effect of a crash, not a deliberate check. It depends on the cv2 behavior measured below.

Not covered

  • Picture or sound quality, and whether a frame matches its scene.
  • A frame file changed or removed by something outside the two tools.
  • A complete PNG with wrong pixels, such as a bad GPU render.
  • Two render jobs on one folder.
  • A scene rebuild while a render runs. The model waits, because Blender loads the scene once.
  • post.py sheet, mix.py, measure.py, and build_scene.py.
  • Any way to detect an old frame other than file times. PostChecksScene looks only at build/scene.blend against the frame file times, so a repair with another method needs a new case in check.py.
  • Anything outside the model's bounds, as section 4 explains.

Measured once, and not rechecked by the command

check.py does not run real Blender or real cv2. These results were measured once, and the fakes assume them:

Blender writes a PNG straight to the final name
Measured with Blender 5.2.1 on Windows, with a CPU render of the test scene. The real render used the OptiX GPU. A later Blender can differ. Only 0 bytes and the full size were seen, across 178,432 folder polls in one run.
cv2.imread gives None on a PNG cut short
Measured with cv2 4.13.0 at 9 cut positions, on Windows Python 3.13. A later cv2 can differ, and post.py does not pin a cv2 version. If cv2 started to return partial images, OKMeansNoDamagedFrame could break, and the check would not see that.

A further limit: the code facts come from scripted cases. check.py also compares the two files with the recorded commit and reports a difference, so a change that the cases miss still shows as a code change for a person to read.

7. How to rerun the check

Run this in WSL from the repo root. It takes about 15 seconds. A fresh clone does not have this script: see the .gitignore whitelist below.

python3 .claude/skills/verify-frame-pipeline/check.py
ExitMeaningDo this
0Every rule holds.This can occur only after all 5 bugs are repaired. A repair gives exit 2 first, because code facts change. Then update KNOWN_FINDINGS and EXPECTED in check.py, and the sync commit in SKILL.md.
1Only the known findings break, and no code fact changed. This is the current result.Your change added no break. The 5 findings stay open.
2A new rule breaks, a finding stopped breaking, or a code fact changed.Read which fact changed. Replay the path against the real code. A step that cannot happen means the model is wrong. If every step can happen, the code has a bug.

Options:

  • --tools DIR checks a copy of render_frames.py and post.py in place of tools/.
  • --out DIR writes the spec, a configuration with all rules, and view.mjs to a new folder outside the repo. Give these to pstack's /statechart skill to get the shortest paths in plain words.

Set PYTHONDONTWRITEBYTECODE=1 to keep the check from writing a cache file. Without it, the check writes tools/__pycache__/post.cpython-312.pyc. Git ignores that folder.

Keeping the check true: the maintain skill

A model can pass while it describes code that no longer exists. The generated skill records the commit where the model last matched the code:

sync-commit: 1ffe98ee21f26ae40679f953f5a1f78eceb6406f

After merges or edits that skipped the check, type /pstack:maintain-formal-verification-skill in Claude Code in WSL. That pstack skill reads each change since the sync commit, updates the model from the code, reruns the check, and proves that an updated check can still fail. It gives each check one outcome:

  • in sync: no change alters what the check describes, and the check passes.
  • updated: the verification now describes the new code, and the check passes.
  • bug: the verification describes the current code, and the code breaks the property.
  • blocked: the check could not be brought back in line or could not run.

Today, with bugs 1 to 5 open, the check does not pass on the current code, so expect the bug outcome for those rules. pstack is enabled at project scope for this folder in WSL Claude Code only. Typed /pstack: commands were not tested. Those skills do not start by themselves, so you must type the command.
